로봇을 정의하는 곳이다. composition.yaml 한 파일이 이 로봇의 구성(팔 2개·리더·카메라 3대)을 선언한다. 나머지는 모두 이 선언에서 생성된다.

선언은 두 가지다. composition.yaml 은 어떤 모듈을 쓰는지를, urdf/pl2_m.urdf.xacro 는 그 모듈이 몸체 어디에 붙는지를 정한다. 좌표 같은 실제 값은 description 패키지가 가진다. 여기에는 이름만 적는다.

generate.sh 를 실행하면 스키마·파라미터·URDF 가 generated/ 에 생성된다. 로봇 기동은 robot.launch.py 한 곳이며, board 인자를 받은 머신의 컴포넌트만 뜬다.

자세히 보기 →

기체마다 다른 값을 모아 두는 곳이다. 코드가 아니라 측정값·설정값이다. 호스트별 파일은 gitignore 하고, 저장소에는 .example 템플릿만 커밋한다.

boards/ 는 보드별 장치와 네트워크 예산, rigs/pl2m-001/ 은 이 기체 한 대의 캘리브레이션·배선·카메라 기록이다. payload 커미셔닝 결과도 이 파일에 저장된다.

rig 기록의 module_revision 은 안전장치다. 측정 당시의 팔 모델을 기록해 두고, composition 의 모델과 다르면 기동을 거부한다. 오래된 캘리브레이션이 새 모델에 적용되는 사고를 막는다.

자세히 보기 →

팔 도메인 저장소다. 제품 PL-2 ARM 에 해당한다. 실물은 OpenArm v2 팔 2개, DAMIAO 모터, CAN-FD 버스, 카메라 3대다.

패키지 13개는 층 구조다. 형상 데이터 → 모터 구동(실물/시뮬레이션) → 안전 게이트 → 팔의 능력(계획·조그·게인·실측) → 화면·조립 순이다.

팔이 외부에 제공하는 인터페이스(관절 그룹·토픽·QoS)는 contract/ 의 계약 파일에 데이터로 선언한다. 조립 계층은 이 계약만 읽는다.

자세히 보기 →

VicPinky 모바일 베이스의 자리다. 현재는 README 만 있다.

주행 계약이 만들어지면 composition.yaml 에 drive 모듈로 추가된다. 이동 중 팔 고정, 단일 E-stop 같은 주행·팔 결합 규칙도 그때 함께 들어온다.

사람이 손으로 잡고 움직이는 교시(텔레옵) 입력 장치다. 현재 실물은 Feetech OpenArm Mini 2대다. 판매 제품 PL-2 LEADER(dynamixel)는 구현 대기 상태다.

이 저장소는 장치의 관절값을 읽어 leader_state 토픽으로 발행하는 것까지만 한다. 팔이 이를 따라 움직이는 방식은 조립 계층(pl_adapters)이 정한다. 그래서 이 저장소에는 팔 관련 코드가 없다.

하드웨어 교체는 backend 파라미터 하나로 한다(mini·dynamixel·bandi·mock). 미구현 백엔드를 지정하면 명확한 에러로 종료된다.

데이터 수집 → 학습 → 추론을 담당한다. 코드에 로봇 이름이 없다. 로봇 정보는 resolver 가 생성한 schema.json 에서만 얻는다. 로봇이 바뀌어도 이 저장소는 수정하지 않는다.

구성: lerobot_ros2(스키마를 읽어 lerobot 에 연결), recorder(에피소드 녹화), inference(정책 실행), studio(운영자 콘솔), policy_server(GPU 서버).

에피소드마다 스키마 해시를 기록한다. 로봇이 바뀌면 기존 데이터셋에 추가 녹화가 거부되고 새 데이터셋으로 시작한다. 서로 다른 로봇의 데이터가 섞이는 것을 막기 위한 장치다.

로봇 종류와 무관한 조립 계층이다. 모듈 계약 + 로봇 선언 + 설정을 읽어 파라미터와 스키마를 생성한다(resolver).

resolver 는 순수 함수다. 같은 입력이면 같은 출력이 나오고, 검증에 실패하면 로봇이 아예 기동하지 않는다.

로봇 무관 원칙은 CI 가 강제한다. 이 저장소에 제품명 문자열이 들어오면 빌드가 실패한다. 자체 검증은 reference_robots/ 의 가상 로봇 3종으로 한다.

팔의 형상 데이터다. URDF, 3D 메시, 모델별 값(v1/v2)을 가진다.

여기서 만들어진 /robot_description 하나에서 모든 것이 파생된다. 중력보상, 안전 한계, 시뮬레이션, MoveIt 이 전부 이 문서를 읽는다. 형상이 바뀌어도 소비하는 쪽 코드는 수정할 필요가 없다.

관절 한계는 joint_limits.yaml 에 있다. 기준은 오른팔이고 왼팔은 부호를 뒤집어 자동 생성한다(거울상).

실물과 같은 인터페이스로 MuJoCo 물리를 구동한다. 상위 계층은 실물과 시뮬레이션을 구분하지 못한다. 컨트롤러·계획·UI 를 그대로 재사용하기 위한 구조다.

3D 모델(MJCF)과 구동 코드를 한 패키지에 둔다. 모델과 코드는 항상 함께 갱신되어야 하기 때문이다.

모델의 소비자는 시뮬레이션만이 아니다. payload 실측 계산과 3D 뷰어도 같은 모델을 쓴다.

팔로 가는 모든 명령이 거치는 관문이다. 명령을 보내려면 먼저 lease(명령권)를 얻고, heartbeat 로 살아 있음을 계속 증명해야 한다.

정책(Python)은 판단을 맡는다: lease 관리, E-stop, 한계 초과 거부. 집행(C++ 컨트롤러)은 차단을 맡는다: 모터 명령 인터페이스를 독점해 우회 경로를 물리적으로 없앤다.

정책이 죽으면 게이트가 팔을 그 자리에 정지시킨다(fail-closed). 감시자가 사라지면 자동으로 안전한 상태가 된다.

목표 자세를 주면 경로를 계획하고 실행한다. MoveIt 2 설정(v1/v2)과 호출 방법에 대한 지식을 담는다.

별도 노드는 없다. move_group 이 이미 서비스를 제공하므로 설정과 클라이언트만 가진다.

서비스 호출로 켜고 끈다. 스튜디오 없이 다른 프로그램에서도 그대로 쓸 수 있다.

팔의 강성(뻣뻣함)을 조절한다. 저수준 제어식은 τ = kp·Δq + kd·Δq̇ + τ_ff 이고, 이 패키지는 그 값을 안전하게 바꾸는 절차를 안다.

무중력 모드(직접 교시)와 중력 방향 관찰 노드를 포함한다. 관찰 노드는 /robot_description 에서 팔 구조를 읽으므로 로봇이 바뀌어도 코드 수정이 없다.

팔이 쥔 물건의 무게와 무게중심을 측정한다. 몇 개 자세에서 토크 오차를 재고 회귀로 계산한다.

CalibratePayload 액션으로 실행하며, 결과는 rig 기록에 저장되어 다음 기동부터 반영된다.

텔레메트리, 3D 뷰, 동작 계획, 조그, 임피던스 실험, payload 실측을 한 화면에서 다루는 데스크톱 앱이다.

특별한 권한은 없다. 모든 동작이 공개 ROS 인터페이스 호출이다. 팔을 움직이려면 다른 프로그램과 똑같이 lease 를 얻어야 한다.

실물이 없으면 미리보기 모드로 열리고, 관절 제어에 들어가면 시뮬레이션을 자동으로 띄운다.

자세히 보기 →

카메라 장치는 이 서버만 연다. 데이터가 필요한 쪽(녹화·추론·비전 기능)은 전부 ZMQ 구독자로 받는다. 장치를 직접 여는 것은 금지다.

서버는 항상 켜져 있다. 구독자가 생기거나 사라져도 장치를 다시 열지 않으므로, 용도 전환(추론 → 비전 기능)이 끊김 없이 된다.

디렉터리 이름과 달리 import 이름은 pl_camera_server 다. 이 이름이 데이터셋 기록에 들어가 있어 바꾸면 기존 데이터셋과 호환이 깨지기 때문에 유지한다.
